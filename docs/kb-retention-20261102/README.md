# DSH 知识库索引持续增长修复

每次变化的会话更新会重新发布完整代际快照。原始实现复用向量计算，但没有旧代回收；10 月 27 日仅打到 node_modules 的补丁在后续安装后丢失。本次把生命周期处理纳入桌面规范源码 `peer/knowledge-link/kb/`，正常 peer/knowledge 插件安装会一起复制。

- 成功建库、无变化更新、迁移后回收无引用的索引代与来源缓存。保留 CURRENT、PREVIOUS、正在检索的代及最近十分钟的目录。只有保留代的清单及每个分片哈希全部通过才开始回收。回收失败不撤销成功发布的新索引，返回可见错误。
- 建库、回退、手动回收共用 writer lock。检索和分类统计持有代内读租约，删除旧代前先改名，再复查租约，避免读者刚接入时被删。
- 新代用硬链接共享与当前代内容哈希相同的不可变分片。变化的分片重新写入；不能硬链接时正常写入。文件格式、模型、分块粒度、资料范围均保持。共享文件必须保持不可变，修复文件应使用原子替换。
- 自动召回更新间隔从十分钟变为三十分钟；无变化、失败或尚无索引时也按触发时间限制重试。手动更新及明确资料导入不受此节流限制。
- `node kb/kb.cjs gc --config /实际配置` 默认预览；显式 `--apply` 才执行手动回收。不删除原笔记、会话、模型、隐藏隔离目录、未知材料或符号链接。

保留代数是生命周期约束，不是整个知识库的硬字节配额。活跃读者和近期目录可让代数暂时超过两代。知识本身增加时，当前有效索引也会正常增大。目录分配占用会重复计算硬链接，不能用它冒充 APFS 实际释放量。

测试：`node --test peer/knowledge-link/kb-retention.test.mjs peer/knowledge-link/automatic-recall.test.mjs peer/knowledge-link/shared-recall.test.mjs`。测试实际写入小型索引、查询、回退、并发暂停、损坏与失败重试，并核验共享 inode。完整现场知识库另做同一查询命中与片段哈希对比。

用户最初确认另一个任务负责旧索引清理，本聊天等待该任务结束且用户确认应用修复后才替换运行文件。复查仍剩二十六代，先生成 `live-gc-plan.json`、完整校验当前及上一代，再用新回收器首次实际执行：移除二十四代残留及八十六份失效缓存，保留两代。此次磁盘可用净增 95,588,839,424 字节；其他任务之前清掉的空间不计入本回执。

源码及当前 profile 引擎均已修复，未发布新安装包。主进程正常重启后才加载三十分钟节流；索引子进程每次新启动就读取当前磁盘引擎代码。没有为应用此修复重启 DSH。

部署：`python3 -B docs/kb-retention-20261102/deploy.py` 先预览，`--apply` 才替换七个文件。只接受已核对的前版本或本次完整代码，持有 writer lock，逐文件核对并原子替换，备份在 `runtime-before/`。两个文件替换后故障注入的隔离实测已验证逐字节回退，新模块也会移除。`deployment.json` 是实际部署记录，`deployment-recovery.json` 是故障恢复回执。
